# Moon Delivery Ops

Игровой симулятор лунной доставки пайков. Игрок выбирает ровер и заказ на карте, оценивает вес груза, заряд батареи и риск зоны, запускает рейс. Цель смены — заработать максимум кредитов за 7 дней и не уронить рейтинг базы до нуля.

## Стек

- **Frontend**: React + TypeScript + Vite, стили — Tailwind CSS
- **Backend**: Node.js + TypeScript + Fastify
- **База данных**: SQLite (`better-sqlite3`) через Drizzle ORM
- **API**: REST, валидация тела запросов — Zod
- **Тесты**: Vitest
- **Контейнеризация**: Docker + Docker Compose

## Как запустить

Локально:

```bash
npm install
npm run dev
```

Команда поднимает клиент и сервер параллельно: игра открывается на `http://localhost:5173`, API — на `http://localhost:8787` (Vite проксирует `/api` на сервер, см. `vite.config.ts`).

Через Docker:

```bash
docker compose up --build
```

Приложение (уже собранный клиент + сервер в одном процессе) слушает `http://localhost:8787`. SQLite-файл сохраняется в volume `moon-data`, так что прогресс переживает перезапуск контейнера.

Продакшн-сборка вручную:

```bash
npm run build   # tsc -b + vite build → dist/ и dist-server/
npm start        # node dist-server/server/index.js
```

## Проверки

```bash
npm test          # vitest, покрывает shared/game.ts
npm run build      # проверка типов + сборка клиента и сервера
```

## Что сделано

- Игровой цикл: выбор ровера/заказа на карте → оценка маршрута (дистанция, расход батареи, время, риск, ожидаемая награда) → запуск рейса → результат (успех/срыв) влияет на деньги, рейтинг, батарею, статус заказа и журнал событий.
- Смена суток («День»): подзаряжает роверы, чинит ровер на ремонте, списывает содержание базы, просрочивает заказы с истёкшей срочностью.
- Карта с зонами разного риска/скорости, кратерами и анимациями (радар у базы, пульсирующие маркеры опасных заказов, «бегущий» пунктир маршрута).
- Полноценный REST API с персистентным состоянием в SQLite — прогресс не теряется между сессиями, есть эндпоинт сброса игры.
- Тесты на ключевые правила: расход батареи от веса груза, блокировка рейса при перегрузе, обновление состояния после доставки.
- Frontend разбит на компоненты (`App`, `MoonMap`, `ControlPanel`, `Objective`, `EventLog`, мелкие UI-примитивы) вместо одного файла.

## Как устроена логика игры

Вся игровая логика — в `shared/game.ts`, она общая для клиента (предпросчёт маршрута перед запуском) и сервера (источник истины при выполнении команд):

- **`calcRoute(order, rover)`** — считает маршрут: расстояние до базы, расход батареи (дистанция + вес + штраф за медленную зону), время в пути, риск (риск заказа + риск зоны + вес), ожидаемую награду (штраф за низкую срочность). Возвращает также флаги `canCarry` / `hasBattery` / `isReady`.
- **`canDeliver(route)`** / **`getImpossibleReason(route)`** — можно ли лететь и почему нет (не хватает батареи, груз тяжелее грузоподъёмности, ровер не готов).
- **`launchDelivery(state, roverId, orderId)`** — ядро рейса: пересчитывает маршрут, бросает исключение если рейс невозможен, иначе бросает «виртуальную монетку» через `successScore = 100 − risk + rating × 0.12 + urgency × 4 ≥ 46`. По результату обновляет деньги, рейтинг, батарею и позицию ровера, статус заказа (`delivered` / `failed`), добавляет запись в `deliveries` и событие в журнал.
- **`advanceDay(state)`** — смена суток: заряжает роверы (сильнее — если были на зарядке), снимает ровер с ремонта после 2-го дня, списывает 35 cr на содержание базы, снижает срочность открытых заказов и переводит их в `expired`, если срочность упала до 0, штрафует рейтинг за каждый просроченный заказ.
- Зоны (`zones`), стартовые роверы и заказы (`initialRovers`, `initialOrders`) — статичные константы, включая заведомо невозможный сценарий (`o-105`, сверхтяжёлый груз, который не влезает ни в один готовый ровер).

Сервер (`server/index.ts`) — тонкий слой поверх этой логики: читает состояние из `store`, вызывает нужную функцию, пишет результат обратно и отдаёт клиенту JSON с примешанными зонами.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/game` | Текущее состояние игры |
| POST | `/api/select` | Выбрать ровер и/или заказ |
| POST | `/api/deliveries` | Запустить рейс (`roverId`, `orderId`) |
| POST | `/api/day` | Перейти к следующему дню |
| POST | `/api/reset` | Сбросить игру к стартовому состоянию |
| GET | `/api/route/:roverId/:orderId` | Предпросчёт маршрута без запуска |

## Где хранятся данные

SQLite-база по пути из `DATABASE_URL` (по умолчанию `./data/moon-delivery.sqlite`, в Docker — `/app/data/moon-delivery.sqlite`, вынесен в volume). Схема — в `server/db/schema.ts`, пять таблиц:

- `game_meta` — день, деньги, рейтинг, выбранные ровер/заказ (одна строка, `id = 'current'`)
- `rovers`, `orders` — текущее состояние роверов и заказов
- `deliveries` — история завершённых рейсов
- `events` — журнал событий базы

`server/db/store.ts` (`createStore`) при каждом `write()` полностью перезаписывает все таблицы внутри одной транзакции — простая, но надёжная схема для однопользовательской игры без конкурентного доступа. Если базы ещё нет, `read()` создаёт стартовое состояние через `createInitialGameState()` из `shared/game.ts`. `reset()` возвращает игру к этому же стартовому состоянию.
